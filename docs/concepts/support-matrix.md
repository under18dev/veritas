# Support matrix

What the current release supports: features, the formal subset, environments and external tools. For the meaning of each result, see [Semantics](/concepts/semantics).

## Formal subset

| Construct                                                                                                                                                                           | Supported            |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------- |
| Parameters/results of type `number` (as bounded safe integers) or `boolean`                                                                                                         | Yes                  |
| Record parameters: object types (literal, `interface` or `type` in the same file) whose properties are all `number` or `boolean`; read as `p.field`                                 | Yes (not as results) |
| Array parameters (`number[]`, `boolean[]`, `readonly`, `Array<T>`) up to `formal.maxArrayLength` elements; `xs.length` and `xs[k]` with a literal `k`                               | Yes (not as results) |
| Passing a record to a function in the same file: a record parameter with exactly the same fields, or an object literal listing each field once (`g({ total: o.total, vip: true })`) | Yes                  |
| Passing an array parameter with the same element type to a function in the same file                                                                                                | Yes                  |
| Nested records, optional properties, returning or copying a record/array, extra or missing fields, spread, computed keys, array literals, computed indexes, array methods           | Unsupported          |
| `if`/`else`, ternary, `return`, `const`                                                                                                                                             | Yes                  |
| `+ - *`, comparisons, `=== !==`, `&&`, `\|\|`, `!`, unary `-`                                                                                                                       | Yes                  |
| Calls to other supported functions in the same file                                                                                                                                 | Yes (no recursion)   |
| `/`, `%`, `**`, floats, `NaN`, `Infinity`, `==`, `??`, casts                                                                                                                        | Unsupported          |
| Loops, `let`/`var`, side effects, async, generators, `this`, external state                                                                                                         | Unsupported          |

Lean proofs cover integer, boolean and record parameters; a property over arrays is `unsupported` with the Lean backend. Property-based tests draw inputs from the same subset (bounded integers, booleans, and records and arrays of them); strings, floats, `NaN`, `Infinity` and Unicode text are never generated.

## Test runners

| Runner                            | Detected from                                                                                                                                                                                              | Tests run with                                                                                                 | Mutation testing                                                                                                                                                                                                                                                            |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Vitest                            | `vitest.config.*`, `vitest` in package.json, a test script that runs `vitest`                                                                                                                              | `vitest run` with the JSON reporter                                                                            | Needs Vitest 4 or later: `@mizchi/mutator` declares Vitest 5 and also runs Vitest 4 projects, with a warning. On Vitest 3 and earlier, `mutate` is reported as `unsupported` and the other stages still run                                                                 |
| Jest                              | `jest.config.{js,ts,mjs,cjs,cts,json}`, a `"jest"` key or `jest` in package.json, a test script that runs `jest`                                                                                           | `jest --json`, started with `node --experimental-vm-modules`                                                   | Experimental, as `@mizchi/mutator` marks its Jest support: Jest 30, native ESM projects only (`"type": "module"`), no Jest `projects`. Other projects get `unsupported` with the reason. `doctor` shows the mutator as `degraded`, and every mutation run carries a warning |
| Node.js test runner (`node_test`) | A script that runs `node --test` (also `node --import tsx --test`, and through launchers such as `cross-env` or `npx`), or a file that imports `node:test` when package.json declares no other test runner | `node --test` with the Node.js that runs Veritas and a reporter bundled with Veritas that writes a JSON report | Unsupported: `@mizchi/mutator` drives only Vitest, Jest and Playwright. `doctor` shows the mutator as `unavailable`, the `mutate` feature is disabled, and the mutate stage of `veritas run` is `unsupported`. No mutation evidence is collected (see below)                |

When a project shows more than one runner, `init` prefers one it can run: an installed runner over one that is only declared, and either over one that only a config file or a package.json key points at, so a Jest config left from a migration does not win over an installed Vitest. Among equals it takes the one the `test` script runs (as a command, not a word in an argument), then the only one with a config file or a dependency. If nothing tells them apart, it chooses Vitest, says so, and (in a terminal) asks. A configuration without `analysis.testFramework` means Vitest.

The Node.js test runner is built into Node.js, so `init` never chooses it just for being available: it shows up when a package.json script runs `node --test`, or, when package.json declares no other test runner (Vitest, Jest, Mocha, AVA, tap, tape, Jasmine, uvu), when a file imports `node:test`, and it counts as installed only when the `test` script runs it or no other runner shows up at all. So a Vitest project whose dependencies are not installed yet still gets Vitest (and `VITEST_NOT_FOUND` when only its config is there), even with a `bench` script that runs `node --test`. Such a file alone never tells runners apart: in a monorepo whose root has Vitest installed and one package tested with `node --test`, `init` keeps Vitest and marks the choice ambiguous. When a file that imports `node:test` matches Node's default test patterns (`**/*-test.*`, `**/*_test.*`, `**/test-*.*`, `**/test/**/*.*`, with the extensions `ts`, `mts`, `cts`, `js`, `mjs` and `cjs`), `init` proposes them as `analysis.testInclude`.

With Jest, what `jest.mock` does depends on how the tests run. Babel and ts-jest compile them to CommonJS and hoist `jest.mock` above the imports, so it replaces the module and Veritas records a mock. In native ES modules (`"type": "module"` with no Babel config, no compiling transformer, and a Jest config whose `transform` is absent or empty and that has no `preset`; when in doubt, Veritas keeps counting `jest.mock` as a mock) the static imports are bound before `jest.mock` runs and the tests reach the real code, so Veritas does not count it as a mock of them; `jest.unstable_mockModule` followed by a dynamic `import()` is the ESM way, and what such an import loads is reported as unknown.

With the Node.js test runner, Veritas reads `test`/`it` and `describe`/`suite` from `node:test` (named, aliased, or the default import `import test from 'node:test'`, also through its members such as `test.describe` and `test.it`), `.skip`/`.todo`/`.only` and the same as an options object (`{ skip: true }`, `{ skip: 'reason' }`, `{ todo: 'later' }`, `{ only: true }`), the hooks `before`/`after`/`beforeEach`/`afterEach`, and the `mock` API (`mock.fn`, `mock.method`, `mock.getter`/`mock.setter`, `mock.module`). Every value export of `node:assert`, `node:assert/strict` and `assert` counts as an assertion (`assert(x)`, `assert.equal`, named imports such as `strictEqual`, `assert.strict.*`, `require`); a call counts only when its name resolves to that import, so a local function of the same name does not. So does `t.assert.*` on the test context and on the contexts of its subtests. CommonJS test files that bind them with a top-level `const { test } = require('node:test')` or `const assert = require('node:assert')` are read the same way, including modifiers read on a required member (`require('node:test')['describe']['skip']`, `test['skip'](...)`), and `node:assert` required inside a test; `require` counts only when the file does not declare its own. CommonJS has no default export, so `require('node:test').default` and `const { default: test } = require('node:test')` register nothing, while `import { default as test } from 'node:test'` does. Subtests (`t.test`) are analysed as part of the test that registers them, not listed on their own. With any runner, a test file matching `analysis.testInclude` from which no test registration can be read (its tests are registered by code static analysis does not follow) is named in the messages of the `map` stage, which is then `partial`, so the run cannot report `pass`. Only files that use the runner, themselves or through a local module they load (they import or require its module, or call its API), are named, so a helper that only re-exports the runner (`export { test } from 'node:test'`) or never uses it is not. A file is left out only when it is shown not to use the runner: one that loads code at run time (a dynamic `import()`, `require` of a name that is not a literal or through another name, `createRequire`, `eval`) or reaches code static analysis does not follow is still named. A file that calls into a package while it loads (`import { suite } from 'some-lib'; suite()`, also under `if`, a loop, `try` or in a function called where it is written; other than packages that only assert or mock) is named too, since it may register tests through it. A file that uses another runner's API (`bun:test`, `Deno.test`) is named with that reason. The message names the first 10 files and counts the rest.

When Veritas runs these tests, it runs `node --test` from the project root with Node's default file patterns, not the project's test script, so extra flags such as `--import tsx` or custom globs in that script are not applied. The bundled reporter writes its JSON report inside `.veritas/improve/`. Tests are keyed `<file>::<suite > test > subtest>`, and skipped and todo tests count as skipped. TypeScript tests run through Node's type stripping, so they must use erasable syntax and import `.ts` file names.

Because there is no mutation testing with the Node.js test runner, no test can be `meaningful_with_evidence`. Tests that assert project results are `inconclusive` (detection power was not measured), weak tests can still be `weak_or_incomplete` from static boundary evidence, and tautological ones `tautological_or_disconnected`.

Tests marked to pass only when they fail (Vitest's `it.fails`, Jest's `it.failing`) get the `expected_failure` modifier and are always assessed as `inconclusive`: their kills and survivors mean the opposite of what their assertions read as.
