# 対応環境

現在のリリースが対応している機能、形式的な部分集合、環境、外部ツールの一覧です。各結果の意味は[セマンティクス](/ja/concepts/semantics)を参照してください。

## 形式的な部分集合

| 構文                                                                                                                                                                     | 対応                       |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------- |
| `number`（有界な安全な整数として扱う）または `boolean` の引数と戻り値                                                                                                    | 対応                       |
| レコードの引数。プロパティがすべて `number` か `boolean` のオブジェクト型（リテラル、または同じファイルの `interface` / `type`）。`p.field` として読む                   | 対応（戻り値には使えない） |
| 配列の引数（`number[]`、`boolean[]`、`readonly`、`Array<T>`）で、要素が `formal.maxArrayLength` 個以下。`xs.length` と、リテラルの `k` による `xs[k]`                    | 対応（戻り値には使えない） |
| 同じファイルの関数にレコードを渡すこと。フィールドがまったく同じレコードの引数か、各フィールドを一度ずつ書いたオブジェクトリテラル（`g({ total: o.total, vip: true })`） | 対応                       |
| 同じファイルの関数に、要素の型が同じ配列の引数を渡すこと                                                                                                                 | 対応                       |
| 入れ子のレコード、省略可能なプロパティ、レコードや配列を返す・コピーすること、フィールドの過不足、スプレッド、計算したキー、配列リテラル、計算した添字、配列のメソッド   | 非対応                     |
| `if`/`else`、三項演算子、`return`、`const`                                                                                                                               | 対応                       |
| `+ - *`、比較、`=== !==`、`&&`、`\|\|`、`!`、単項の `-`                                                                                                                  | 対応                       |
| 同じファイルにある、対応するほかの関数の呼び出し                                                                                                                         | 対応（再帰は不可）         |
| `/`、`%`、`**`、浮動小数点数、`NaN`、`Infinity`、`==`、`??`、型の変換                                                                                                    | 非対応                     |
| ループ、`let`/`var`、副作用、async、ジェネレーター、`this`、外部の状態                                                                                                   | 非対応                     |

Lean の証明が扱うのは整数、真偽値、レコードの引数で、配列についての Property は、Lean のバックエンドでは `unsupported` になります。property-based テストの入力も同じ部分集合から作ります（有界な整数、真偽値、それらのレコードと配列）。文字列、浮動小数点数、`NaN`、`Infinity`、Unicode のテキストは生成しません。

## テストランナー

| ランナー                                | 検出の手がかり                                                                                                                                                                                                                  | テストの実行                                                                                                 | mutation テスト                                                                                                                                                                                                                                                                                                                                      |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Vitest                                  | `vitest.config.*`、package.json の `vitest`、`vitest` を実行する test スクリプト                                                                                                                                                | JSON レポーターを付けた `vitest run`                                                                         | Vitest 4 以降が必要です。`@mizchi/mutator` が対応を宣言しているのは Vitest 5 で、Vitest 4 のプロジェクトも警告付きで実行します。Vitest 3 以前では `mutate` を `unsupported` として報告し、ほかのステージはそのまま実行します                                                                                                                         |
| Jest                                    | `jest.config.{js,ts,mjs,cjs,cts,json}`、package.json の `"jest"` キーや `jest`、`jest` を実行する test スクリプト                                                                                                               | `node --experimental-vm-modules` で起動した `jest --json`                                                    | 実験的です。`@mizchi/mutator` 自身が Jest への対応を実験的としているためです。Jest 30 で、ネイティブ ESM のプロジェクト（`"type": "module"`）だけが対象で、Jest の `projects` には対応しません。それ以外のプロジェクトでは理由を付けて `unsupported` と報告します。`doctor` は mutator を `degraded` と表示し、mutation の実行には毎回警告が付きます |
| Node.js のテストランナー（`node_test`） | `node --test` を実行する package.json のスクリプト（`node --import tsx --test` や、`cross-env`・`npx` などのランチャー経由も含む）。package.json がほかのテストランナーを宣言していなければ、`node:test` を import するファイル | Veritas を動かしている Node.js の `node --test` に、Veritas 同梱の JSON レポートを書くレポーターを付けて実行 | 非対応です。`@mizchi/mutator` が扱えるのは Vitest、Jest、Playwright だけです。`doctor` は mutator を `unavailable` と表示し、`mutate` の機能は無効になり、`veritas run` の mutate ステージは `unsupported` になります。mutation の証拠は集まりません（後述）                                                                                         |

複数のランナーが見つかったとき、`init` は実行できるものを優先します。インストール済みのランナーは宣言だけのものより、どちらも設定ファイルや package.json のキーだけで示されるものより優先するので、移行の名残の Jest の設定が、インストール済みの Vitest に勝つことはありません。同じ順位のものの中では、`test` スクリプトが（引数の中の単語ではなく）コマンドとして実行するものを選び、次に設定ファイルや依存の宣言があるのが 1 つだけならそれを選びます。それでも判断できないときは Vitest を選んでそのことを伝え、ターミナルではどちらを使うか尋ねます。`analysis.testFramework` のない設定は Vitest として扱います。

Node.js のテストランナーは Node.js に組み込まれているので、`init` が使えるというだけで選ぶことはありません。検出の手がかりになるのは、package.json のスクリプトが `node --test` を実行していること、または package.json がほかのテストランナー（Vitest、Jest、Mocha、AVA、tap、tape、Jasmine、uvu）を宣言しておらず、`node:test` を import するファイルがあることです。インストール済みとみなすのは、`test` スクリプトがこれを実行しているときか、ほかのランナーの手がかりがまったくないときだけです。そのため、依存をまだインストールしていない Vitest のプロジェクトは、`node --test` を実行する `bench` スクリプトがあっても Vitest のままです（設定ファイルしかなければ `VITEST_NOT_FOUND` になります）。ただし、そうしたファイルがあるというだけでは、どのランナーかを決める根拠にしません。ルートに Vitest がインストールされていて、1つのパッケージだけを `node --test` でテストしているモノレポでは、`init` は Vitest を選んだうえで、判断があいまいだったことを示します。`node:test` を import するファイルが Node.js の既定のテストのパターン（`**/*-test.*`、`**/*_test.*`、`**/test-*.*`、`**/test/**/*.*`。拡張子は `ts`、`mts`、`cts`、`js`、`mjs`、`cjs`）に当てはまるときは、`init` はそれらのパターンを `analysis.testInclude` として提案します。

Jest では、`jest.mock` の効果がテストの実行方法で変わります。Babel や ts-jest はテストを CommonJS にコンパイルし、`jest.mock` を import より前に移すので、モジュールが置き換わり、Veritas はモックとして記録します。ネイティブ ESM（`"type": "module"` で、Babel の設定もコンパイルする transformer もなく、Jest の設定の `transform` がないか空で `preset` もない。判断できないときは `jest.mock` をモックとして数え続けます）では、`jest.mock` が実行される前に静的な import が結び付けられ、テストは本物のコードを実行するので、Veritas はそれらのモックとして数えません。ESM でのモックは `jest.unstable_mockModule` と動的な `import()` の組み合わせで、そうした import が読み込むものは不明として報告します。

Node.js のテストランナーでは、`node:test` の `test`/`it` と `describe`/`suite`（名前付き、別名、既定の import `import test from 'node:test'` のいずれも。`test.describe` や `test.it` のようにそのメンバーを通しても読みます）、`.skip`/`.todo`/`.only` と、同じ指定をオプションのオブジェクトで書いたもの（`{ skip: true }`、`{ skip: 'reason' }`、`{ todo: 'later' }`、`{ only: true }`）、フックの `before`/`after`/`beforeEach`/`afterEach`、`mock` の API（`mock.fn`、`mock.method`、`mock.getter`/`mock.setter`、`mock.module`）を読みます。`node:assert`、`node:assert/strict`、`assert` が export する値はすべて assertion として数え（`assert(x)`、`assert.equal`、`strictEqual` などの名前付き import、`assert.strict.*`、`require`）。数えるのは、呼び出した名前がその import に解決されるときだけで、同じ名前のローカルの関数は数えません。テストのコンテキストとそのサブテストのコンテキストの `t.assert.*` も同じです。トップレベルの `const { test } = require('node:test')` や `const assert = require('node:assert')` で束縛する CommonJS のテストファイルも、同じように読みます。require したメンバーに続けた修飾子（`require('node:test')['describe']['skip']`、`test['skip'](...)`）や、テストの中で require した `node:assert` も読みます。`require` は、ファイルが同じ名前を自分で宣言していないときだけ数えます。CommonJS には既定の export がないので、`require('node:test').default` や `const { default: test } = require('node:test')` はテストを登録しませんが、`import { default as test } from 'node:test'` は登録します。サブテスト（`t.test`）は、それを登録したテストの一部として解析し、単独では一覧に載せません。どのランナーでも、`analysis.testInclude` に当てはまるのにテストの登録を1つも読めなかったテストファイル（静的解析で追えないコードがテストを登録している場合など）は、`map` ステージのメッセージに名前が出ます。このとき `map` ステージは `partial` になり、実行結果が `pass` になることはありません。名前を出さないのは、テストを登録しないことを示せたファイルだけです。つまり、そのファイルと読み込むローカルのモジュールのすべての文が、読み込まれる間にコードを実行しないとわかっていて、テストを登録するモジュールを import していないファイルです。コードを実行しないとみなすのは、パッケージの規則を満たすモジュールの import と export、関数・型・interface・const か値がリテラルの enum・デコレーターや static ブロックやコードを実行する static 初期化子のない class の宣言、無害な値（リテラル、置換のないテンプレート、関数、spread のないそうした値のオブジェクトと配列、ローカルの名前）で初期化する変数と `export default`、無害な値の CommonJS の export、少数の無害な組み込み（`Symbol()`、`Object.freeze()`、パスと URL のヘルパー）、ランナーのフックとモックの設定（`beforeAll`、`vi.mock`、`jest.setTimeout`）だけです。それ以外の呼び出し、`new`、`await`、ループ、spread、代入、getter を実行しうるメンバーの読み取り、デコレーターはコードの実行とみなします。副作用のためのパッケージの読み込み（`import 'pkg'`）、パッケージ全体の re-export（`export * from 'pkg'`）、パッケージの動的 import は常に数えます。ランナー自身のパターン（`*.test.*`、`*.spec.*`）に当てはまるファイルでは、ローカルの import のどこかで名前付きでパッケージを import することも数えます。ディレクトリの glob だけで当てはまるヘルパーでは、名前付きで import して関数の中でだけ使うパッケージは数えません。これには Node.js のテストランナーで既知の制限があります。`node --test` は `test` ディレクトリの下のファイルをすべてテストファイルとして実行しますが、そうしたディレクトリの glob（`**/test/**`）だけで当てはまるファイルにはゆるいほうの規則を使います。そのため、そこにあってパッケージの import を束縛するだけのファイルは、そのパッケージが import されたときにテストを登録するものであっても、名前が出ません。解決できないローカルのモジュールも数えます。また、静的解析のほかの部分がすでに開いているとみなしたファイル（読み込み時に読めないコードがある、または計算された名前の動的 import やランナーの計算されたメンバーのように追えないコードに届く。ランナーの API の re-export、`require` や `import()` で読み込むローカルの JSON、無害な値の CommonJS の export、ディレクトリの glob だけで当てはまるヘルパーでトップレベルに `require` して関数の中でだけ使うパッケージは、これに当たりません）は、この規則にかかわらず必ず名前が出ます。そのため、`export { test } from 'node:test'` のような barrel や、関数を定義するだけのヘルパーは名前が出ませんが、読み込まれるときに `const app = createApp()` を実行するヘルパーは名前が出ます。実行するコードがパッケージを呼び出しているとき（`import { suite } from 'some-lib'; suite()`。読み込むローカルのモジュールの中の場合も含みます）は、メッセージにそのパッケージとモジュールが出ます。ほかのランナーの API（`bun:test`、`Deno.test`）を使うファイルは、その理由とともに名前が出ます。メッセージに名前が出るのは最初の 10 個までで、残りは数だけを示します。

Veritas がこれらのテストを実行するときは、プロジェクトのルートで Node.js の既定のファイルパターンを使って `node --test` を実行します。プロジェクトの test スクリプトは実行しないので、そこに書いた `--import tsx` などのフラグや独自の glob は適用されません。同梱のレポーターは JSON のレポートを `.veritas/improve/` の中に書きます。テストのキーは `<file>::<suite > test > subtest>` で、skip と todo のテストはスキップとして数えます。TypeScript のテストは Node.js の型の除去（type stripping）で実行するので、消去できる構文だけを使い、`.ts` のファイル名で import する必要があります。

Node.js のテストランナーでは mutation テストを行えないので、`meaningful_with_evidence` になるテストはありません。プロジェクトの結果を assert するテストは `inconclusive`（検出力を測れていない）になります。一方、弱いテストは静的な境界の証拠から `weak_or_incomplete` に、プロジェクトの振る舞いを確かめていないテストは `tautological_or_disconnected` になり得ます。

失敗したときだけ通るテスト（Vitest の `it.fails`、Jest の `it.failing`）には `expected_failure` の修飾子を付け、評価は常に `inconclusive` にします。kill や生き残りが、assertion の見た目と逆の意味になるからです。

## 外部ツールとライセンス

Veritas のライセンスは Apache-2.0 です。使っている外部ツールは次のとおりです。

| ツール                      | ライセンス | 使い方                                           |
| --------------------------- | ---------- | ------------------------------------------------ |
| `@mizchi/mutator`           | MIT        | npm の依存パッケージ。別のプロセスとして実行     |
| `z3-solver`（Z3）           | MIT        | npm の依存パッケージ。WASM のビルド              |
| fast-check                  | MIT        | npm の依存パッケージ。制限したプロセスで実行     |
| Lean 4 と Lake              | Apache-2.0 | 利用者が別途インストール（elan）。同梱しない     |
| `openai`                    | Apache-2.0 | 任意の OpenAI アダプターの npm の依存パッケージ  |
| `@anthropic-ai/sdk`         | Apache-2.0 | 任意の Claude アダプターの npm の依存パッケージ  |
| lightningcss（Vitest 経由） | MPL-2.0    | 変更していない推移的な依存パッケージ。同梱しない |
